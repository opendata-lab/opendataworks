# 问题卡片、计划卡片与计划开关

日期：2026-10-25。状态：需求已由 OntoFoundry 用户确认，实施中（计划见 `docs/plans/2026-10-25-dataagent-plan-and-question-cards-plan.md`）。

## 1. 背景

OntoFoundry 建模需要两种交互：
- 开工前先问几个取舍问题；
- 出一份计划，用户确认后再执行。

现在的做法是运行结束时写一个“待确认”文件。平台把计划存下来，用户回复后再发起新运行，并把旧计划上传回去恢复。这条链路跨了两个系统，用户也没有明确的“确认执行”按钮。

这两种交互都是通用的 Agent 能力，与本体无关，应由 DataAgent 提供：
- 运行停在 `waiting_input` 或 `waiting_permission`；
- 对话组件画卡片；
- 用户回答后，同一个运行接着执行。

DataAgent 已有基础：
- Claude Code 引擎的 `AskUserQuestion` 工具（`core/ask_user_question.py`）；
- 持久等待（`2026-06-26-permission-confirmation-wait-design.md`）；
- 对话组件的 `QuestionCard`。

缺的是：Pi 引擎的同类工具、计划工具、计划开关，以及等待超时。

## 2. 需求

| 编号 | 需求 |
|---|---|
| PQ-01 | **问题卡片**，Pi 与 Claude Code 两个引擎都要支持。<br>一次可提 1～4 个问题，卡片按“1 / 3”分页。<br>每题 2～4 个选项，每个选项有标题和一行说明，可标“推荐”。<br>每题有“补充你的想法，或给出不同的答案…”输入行和“跳过”按钮，右上角“×”跳过全部。<br>答完一题自动翻到下一题，最后一题提交后，同一个运行继续。 |
| PQ-02 | **计划卡片**：沿用 Claude Code 引擎已有的 `ExitPlanMode(plan)`，Pi 引擎补齐同名工具；运行停在 `waiting_permission`，类型为 `plan`。<br>对话中显示卡片：左上角“计划”图标，右上角下载（`.md`）、复制、展开三个按钮；正文显示标题和前几行，下方渐隐。<br>卡片下方是“实施此计划？”，右上角“×”表示不执行（等同不带意见的“先调整计划”），两个选项：<br>· “是，开始执行”：同一个运行继续；<br>· “先调整计划”：展开输入行，用户写的修改意见作为工具结果交给 Agent，Agent 修订后再次调用 `ExitPlanMode`。<br>复制在 HTTP 局域网部署下也要能用（非安全上下文，要有回退）。 |
| PQ-03 | **展开**：组件派发 `dataagent-plan-open` 事件，带 `{markdown, title, body}`，由宿主页面决定在哪里显示全文。OntoFoundry 放在右侧分栏：顶部是计划标题和下载、复制、关闭按钮，正文用去掉首个标题的 `body`，标题不重复。<br>宿主不处理该事件时，卡片原地展开全文，再点一次收起；不用浮层抽屉。 |
| PQ-04 | **计划开关**：输入框左下角的“计划”按钮（灯泡图标），作为权限模式 `plan` 接入。<br>宿主在 `composerConfig.planMode` 中声明是否显示和默认值（OntoFoundry 建模模式默认打开），开关状态随每条消息的 `settings.permission_mode` 发出。<br>打开时，运行在产生写入类结果前必须先调用 `ExitPlanMode` 并得到批准；关闭时由 Agent 自行判断。<br>DataAgent 在模式为 `plan` 时把这一约束写进系统提示。批准前，工具层拦截已登记的写工具：门户写工具，以及 Write、Edit 等改文件的内置工具；两个引擎用的是同一份名单（`permission_gate`）。<br>Bash 和未登记的 MCP 工具不拦截。这与 Claude Code 引擎现有的边界相同：Bash 是只读调研的通道，写入范围由工作区边界限制。所以“批准前不产出结果文件”靠模型遵守提示，工具层不作保证。<br>补充（2026-10-26 内网验证）：Pi 引擎把计划状态通过环境变量 `DATAAGENT_PLAN_STATE` 交给命令（批准前 `pending`，批准后 `approved`），技能里写结果的脚本据此拒绝执行；用户要求调整后状态仍是 `pending`，模型必须重新提交并获批准。Claude Code 引擎不设置该变量，仍只靠提示。 |
| PQ-05 | **等待超时，按推荐继续**：<br>· 问题卡片等待超过 `dataagent_interaction_timeout_seconds`（全局配置，默认 600 秒，0 表示一直等待）仍未回答时，有“推荐”选项的题自动选推荐项，没有推荐的题按“跳过”处理，然后继续运行；<br>· 计划卡片在同一时长后，按 Agent 配置的 `plan_timeout_action` 处理：`approve`（自动执行）或 `park`（停住，见 PQ-06），默认 `park`。OntoFoundry 建模 Agent 也用 `park`：计划必须由用户批准（2026-10-26 用户确认）；<br>· 回答后问题卡片收成一行，例如“✓ 已补充 3 项 · 按订单行 · 扣减 · …”，点开看每题答案；自动作答写成“等待超时，已按推荐选择 N 项”，答案和来源（`source: "auto_timeout"`）写入事件。卡片显示倒计时，用户在倒计时内的操作优先。<br>· 自动作答写库失败（例如 MySQL 短暂断开）时，下一次轮询重试。用户回答和自动作答都通过同一个事务性写入，只有一个生效。<br>· 等待期间只暂停总超时和空闲超时；取消、子进程退出照常检测。取消不作为答案回给模型，直接结束运行。 |
| PQ-06 | **等待期间释放资源**（v1 不做，记入 `docs/TODO.md`；v1 等待期间进程保持，总超时和空闲超时暂停计时）：<br>停住的运行不占用模型调用和执行槽位，状态以事件表为准。<br>`park` 的运行在用户回答后从事件日志恢复，接续原工具调用。不能接续时（如引擎进程已不在），按现有设计结束为 `suspended`，用户的回答作为新一轮的第一条消息发出，不要求用户重说。 |
| PQ-07 | **协议**：沿用现有记录，不新增类型。<br>· 问题：`question_request` / `question_answer`；<br>· 计划：`risk_level=plan` 的 `permission_request` / `permission_decision`。批准是 `allow`；调整是 `deny`，修改意见放在 `note`；<br>· 请求记录带 `deadline_at`（没有截止时间时为空），回答记录带 `source`（`user` 或 `auto_timeout`），历史回放和交互查询原样返回这两个字段；<br>· 回答走现有 `POST {endpoint}/interactions`（`kind` 为 `permission` 或 `question`），宿主 BFF 照现有方式转发，不解析内容。 |

## 3. 常见做法对照

| 产品 | 提问 | 计划 | 超时 |
|---|---|---|---|
| Claude Code | `AskUserQuestion`：多题，每题 2～4 个选项，可标推荐，可填其他答案 | 计划模式：`ExitPlanMode` 提交计划，用户批准或继续修改 | 无超时，一直等待 |
| Codex | 运行中请求用户输入 | 计划模式先出计划 | 批准请求一直等待；无人值守时由策略决定（如自动拒绝或自动允许） |
| 本设计 | 同 Claude Code | 同 Claude Code | 有推荐的题超时按推荐继续，计划按 Agent 配置处理 |

自动按推荐继续适合“产出还要人审”的场景（如 OntoFoundry 的提案），所以做成按 Agent 配置，不作为全局默认。

## 4. 对 OntoFoundry 的影响

上线后，OntoFoundry 做三件事：
- 技能改为通过问题卡片提问、通过 `ExitPlanMode` 交计划，删除“待确认”文件、`prior_plan` 上传与恢复，以及 `awaiting_reply` 状态；
- 构建页打开组件的计划开关，处理 `dataagent-plan-open` 事件，在右侧栏显示计划全文；
- 日常模式改用问数 Agent（话题创建时绑定），建模模式用建模 Agent。

## 5. 验收

- 用两个引擎各跑一次：问 3 题，分别选推荐、填补充、跳过，运行在原任务中继续，事件中能看到三种答案。
- 计划：先调整一次，再批准；只产生一个任务；开关关闭时不强制出计划。
- 超时：把超时时间调到 30 秒，问题按推荐自动作答，卡片显示自动选择；`approve` 的计划自动执行，`park` 的计划一直等待。服务重启后的恢复属于 PQ-06，不在 v1 验收范围。
- 在局域网 IP 的 HTTP 页面上，复制和下载可用。
