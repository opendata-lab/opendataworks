## 首轮评审结论与判断标准（历史快照）

删除 Python MCP → Agent REST 的内部跳板、重复身份上下文、重复凭据传递和查询执行实现，方向成立。四个构建模块也可以成立，但模块数、类数和包名前缀不是熵减指标。

应以“同一事实只有一个权威来源、同一操作只有一条明确主路径、权限语义保持不变、维护者需要理解的隐含状态更少”为验收标准。当前文档有权限回归风险，也有将分散复杂度集中到大服务、把不可用能力整体迁移的倾向，尚不适合直接照单实施。

## 设计与计划需要纠正的事项

### R1 · P1：人工物理 DDL 被改为系统账号执行

- 设计 §3.3.2 第 2、4 项把物理建表、改表列为系统连接用途；计划 Task 3 第 2 项明确调用 `executeSystemSql`。
- 当前 `DorisConnectionService.java:132` 的普通连接使用当前 USER 的数据库映射；`TableEngineJdbcExecutor.java` 也调用这一连接入口。`DorisTableEngineHandler` 的改表、删表最终沿此路径执行。`DorisConnectionServiceUserContextTest` 已锁定“缺映射不使用源凭据”的约束。
- 后果：仅能登录门户、没有原生 DDL 权限的用户，可能通过表设计/结构编辑使用系统凭据执行 DDL。删除隐式开关不能顺便扩大执行权限。
- 修正：人工建表、改表、删表保持主体连接；同步和后台运维才显式使用系统连接。列出每个调用点的用途与账号，验证只读用户 DDL 被原生数据库拒绝、且没有系统连接尝试。
- 文档还分别使用 `executeDdl` 与 `executeSystemSql` 描述同一入口，需统一为能明确表达执行身份的契约。

### R2 · P2：23 个工具中 17 个恒定不可用，仍要求迁移全部实现

- 设计 §2.2、§3.3.1 和计划 Task 5 要求所有 SERVICE 都只能执行 6 个工具，却同时迁移其余 17 个工具的 Schema、DTO 转换、处理器和预览令牌。
- 本期没有任何凭据类型能调用这 17 个工具。保留它们会增加模型候选、稳定失败路径、测试和后续契约维护；只读工作流被误报为“开发写接口”已有真实试用记录，见现有 TODO。
- 建议本期只注册实际支持的 6 个工具，未知/未注册名称由 SDK 拒绝；有资源授权需求时再实现相应工具，不预建开关和多套目录。若确有外部契约要求保留 23 个，先写明消费者证据与收益。
- 这会同步删减当前迁移任务，而不只是把门禁换一个位置。既有服务账号不能写的约束保持不变。

### R3 · P2：`DatasourceAccessService` 职责过宽，已有连接底座被遗漏

- 设计把主体解析、账号映射、权限状态、连接、SQL 执行、双账号检查、可见列缓存和参考 DDL 都合并到一个服务。
- 实际已有 `DatasourceConnectionFactory`，统一驱动校验、连接规格、只读会话初始化和连接失败清理。文档把“五个类有 JDBC 职责”等同于“五套底层连接实现”，会导致再次包装或重写已经统一的底座。
- 建议保留连接工厂；访问服务只负责已授权主体到连接的选择与可见性；查询服务负责只读策略、执行协同、结果读取和审计；方言继续属于现有适配器。提取有真实重复的读取器即可，不建立泛化执行框架。
- 同样，账号服务围绕同一张表不意味着所有认证、管理和 Token 方法都必须合成一个类。应统一状态校验、锁与审计来源，而不是追求服务类数量最少。

### R4 · P2：“六边形边界”与 HTTP 依赖归属不一致

- 设计 §3.2 把 `AuthenticationFilter`、路由策略和 `Result<T>` 放入 core；架构守卫又刻意只禁止部分业务包依赖 Servlet。
- 这允许 HTTP 路径、请求类型和 REST 信封继续驻留所谓协议无关内核。模块依赖图通过，也不能说明协议边界成立。
- 建议仍用四模块：core 放主体、会话/Token 认证服务与领域授权；统一 HTTP Filter 和路由装配放 app，REST 返回信封放 api。无需再拆第五个模块，也无需为每个服务新增 port 接口。
- `runWith` 还需明确嵌套恢复、异常清理及缓存作用域：回调应恢复进入前的上下文，最外层请求结束才完全清除；缓存不能跨主体/委托身份复用。避免把一个新 Holder 变成通用全局属性袋。

### R5 · P2：严格 Schema 尚未形成单一可执行契约

- 设计 §3.4.2 一方面删除 Agent DTO、直接复用领域对象，一方面手写 23 份 Schema，再在 handler 编写必填/范围/未知字段校验。没有明确这些约束的权威来源。
- 现有 Python `task`、`workflow`、`schedule` 是开放 Map。迁移后如果仅对其声明 `additionalProperties:false`、未枚举属性，会拒绝全部有效字段；若放开，则不符合文档“所有对象严格拒绝未知字段”的承诺。
- 修正：每个实际保留工具只有一份可执行 Schema，结构/类型/未知字段校验复用标准 Schema 校验器，业务状态规则由领域服务负责；handler 只转换协议命名与调用。不要再手写一套与 Schema 平行的通用验证逻辑。确需保留的开放扩展字段应按实际契约声明。
- 计划需列清默认值、null 与缺省、snake_case/camelCase、嵌套字段。现有 `output_table_ids` 文档要求不可清空，设计“清空该侧血缘”的描述应明确仅针对允许清空的一侧，不能机械复制到输出血缘。

### R6 · P1：预览令牌依赖被删除，签名与重放语义未设计

- 计划 Task 3 迁移 `AgentPreviewTokenSupport`，Task 4 又删除 `AgentApiProperties`，Task 6 删除 `AGENT_API_SERVICE_TOKEN`。
- 现有签名直接依赖这项密钥；缺失时回退固定字符串 `odw-agent-preview-token-secret`。仅迁移类或删除配置，会留下编译依赖或固定密钥问题。
- 现实现虽称“一次性”，实际只校验工作流、版本和到期时间，没有消费记录，故有效期内可重复验证，也未绑定主体和具体动作。
- 优先按 R2 不迁移当前不可用的 MCP 发布工具与令牌机制。若决定保留，必须在设计中明确用途、签名密钥归属和真实重放语义，禁止固定密钥回退；不得将“短时版本凭证”误称为“一次性授权”。不应为了一个本期不可用工具先建设通用令牌平台。

### R7 · P2：512KB 行预算不能证明 MCP 响应有界

- 设计 §3.3.3 对 rows 使用默认 512KB，§3.4.2 又同时返回 JSON 文本和 `structuredContent`，结果会重复承载，文本还会二次转义。
- 独立探针：包含 250,000 个双引号的单元格，rows JSON 仅 500,010 字节，低于 524,288；装入双份 MCP 工具结果后为 1,500,120 字节，尚未计算 JSON-RPC 外壳。这是序列化结构的验证，不是对某一 DataAgent 客户端当前缓冲阈值的实测。
- 现有 `resultByteBudgetKeepCount` 又强制至少保留一行，600,010 字节的首行仍会返回；且裁剪发生在 JDBC 完整读取返回行之后，并非读取阶段的内存守卫。
- 修正：区分查询结果预算和最终协议响应预算，定义超大单元格/首行处理，读取阶段尽早停止；MCP 适配层对最终序列化信封做明确限制。不要把客户端特定限制全部固化到通用 Web 查询语义中。

### R8 · P2：两份活动方案重复拥有同一改造，部分验收结论冲突

- 收敛方案和历史清理方案都修改认证过滤器/白名单、只读 SQL 守卫、数据源执行器和平台账号持久化，但没有明确唯一任务归属及依赖。一个文档保留 `DataExportService` 的领域归属，另一个要求删除；应明确最终调用图。
- 历史清理方案声称移除 WebFlux 后卸载全部 Reactor；官方 MCP SDK `v0.18.5` 的 `mcp-core` 本身依赖 `reactor-core`。目标应为删除不再使用的 WebFlux starter/Netty，引入 SDK 所需 Reactor 是正常依赖，不得为满足“零 Reactor”错误排除它。
- SDK WebMVC Stateless transport 的 builder 原生配置一个 endpoint；两个别名的装配方式仍需 Task 0 验证，不能直接当已验证能力。该项已有前置实验安排，不要求另建 transport。
- 修正：给重叠项唯一归属，另一计划只链接依赖；明确 Boot 3 升级之后才能使用 `RestClient`，统一构建入口、最终保留类和依赖验收。不增加发布过渡模式。

官方依据：[mcp-core 0.18.5 POM](https://github.com/modelcontextprotocol/java-sdk/blob/v0.18.5/mcp-core/pom.xml)、[WebMVC Stateless transport 源码](https://github.com/modelcontextprotocol/java-sdk/blob/v0.18.5/mcp-spring/mcp-spring-webmvc/src/main/java/io/modelcontextprotocol/server/transport/WebMvcStatelessServerTransport.java)。以上为源码核对，未执行版本兼容工程。

## 沿同一思路新确认的熵增点

### N1 · Dolphin 的执行目标有两份线程状态与默认回退

`DolphinSchedulerService.java:63` 和 `DolphinOpenApiClient.java:49` 分别维护 `ThreadLocal<DolphinConfig>`。前者 `withConfig` 必须同步绑定后者；两层在上下文缺失时又各自选择 active/default 配置。更换 WebClient 为 RestClient 不会消除这项复杂度。

建议执行入口解析一次不可变 Dolphin 目标，后续显式传给客户端；明确需要默认目标的入口只在边界选择一次。保持现有目标与缓存身份规则，不引入新的全局目标上下文。本项是确认存在的重复状态，尚未证明出现跨环境执行事故，单独待设计。

### N2 · 外部用户身份来源标签与实际查询条件不一致

`AuthController.agentUserId` 输出 `<authSource>:<externalId>`，但 `DatasourceSubjectAccountService.resolveUser` 对非 local 来源只约束 `auth_source != 'local'`，没有匹配传入的具体来源。

结果：来源前缀虽出现在身份字符串中，却未参与完整定位；不同来源存在相同 externalId 时可能选错或出现多行错误。当前未连接真实第三方 OAuth，不能宣称发生了生产冒认。

建议统一身份解析职责，非 local 按 `(auth_source, external_id)` 精确定位，并核对实际来源枚举与唯一性规则。该问题独立于已延期的可信身份签名；修正来源解析也不代表 `X-Agent-User-Id` 成为可信自然人身份。

### N3 · HTTP 跨域与 MCP 入口策略未归口

现有 `WebConfig.java:29` 任意回显 Origin 并允许 credentials，统一放行预检；Python MCP 单独关闭 DNS rebinding protection。新设计把入口移入同一进程，却只设计 Token 和私网选项，未明确继承哪套 Origin/Host/预检规则。

官方 SDK 候选版本的 transport security validator 默认是 NOOP，不能把采用 SDK 等同于已自动获得来源校验。私网检查在 Nginx 后通常看到代理地址，也不能代替浏览器来源策略。

建议在 HTTP 装配边界明确一套部署匹配的 Origin/Host 与预检规则、代理信任边界。先依据实际同源/跨域消费者收敛，不新增多套鉴权链。这是已有入口规则分散和集成设计缺项，不是声称存在已验证的浏览器攻击链。

多数据源同名 namespace 的歧义已在 TODO。此次进一步确认：`BackendAgentMetadataService.resolveClusterIdFromTables` 按目录表反查源，注释声称按授权收窄，但查询未这样做；报错建议“通过数据源 ID 定位”，当前 `resolve_datasource`/`query_readonly` 入参却不提供该 ID。保持当前拒绝歧义，不以猜测引擎/选第一个源回退。后续设计明确 sourceId + namespace 的主定位契约时一并处理。

## 建议的实施约束

1. 先修设计中的执行身份、保留工具集、职责归属与令牌依赖，再编写实现；保留现有权限语义。
2. 在一次交付内，按“兼容工程 → 删除无消费者路径 → 核心重复职责收敛 → 模块装配与部署 → 全链路验收”的依赖顺序推进；这是内部实施顺序，不引入双轨发布。
3. 包名前缀整体重命名不能作为熵减成果。若保留这项决定，放在职责确定后机械处理，不与权限规则重新定义混在同一任务。
4. 以唯一主体来源、唯一连接工厂、唯一状态校验/审计写入路径、无恒定失败工具、无隐式系统账号升级、无重复执行目标上下文作为成果；不以“类数越少越好”衡量。

## 修订稿复核：先判断预览令牌是否需要存在

2026-11-03 用户对修订稿“复用 JWT 密钥 + 随机密钥回退 + 主体绑定 + 内存 nonce 消费”提出必要性质疑。本节针对修订后的设计 §3.4、§3.3.2、§3.3.3 与 §3.5.2；前文是上一版评审快照，不能视为全部仍未处理。修订稿已按用户决策保留 23 个工具，本节不再建议缩减工具数量。

### F1 · 一次性预览凭证没有明确业务必要性，不建议继续加固成独立机制

原评审 R6 指出密钥依赖和“一次性”命名不实，是既有实现问题，不代表必须新增真正的一次性消费系统。应先决定是否需要保留凭证，再决定实现，不能把“纠正名实不符”变成新的功能要求。

现有 `WorkflowPublishService.handleDeploy` 在执行部署前重新构建预览，检查 `canPublish` 与差异确认标记；`WorkflowScheduleService.onlineSchedule` 也会检查调度与工作流当前状态。需要保留和统一这些执行前检查，而不是让 MCP 为同一业务另建发布安全规则。

- 如果目的是让模型先看到差异，preview 是只读辅助工具，调用顺序写入工具说明/Skill 即可；这不是可强制证明的用户确认。
- 如果目的是用户批准，模型自己可以连续调用 preview 与 publish，签名令牌证明不了用户批准。
- 如果目的是防止预览后版本变化，需要在实际执行的并发控制边界检查预期版本/状态。新 nonce 不解决令牌校验后、执行前状态变化，也没有绑定外部 Dolphin 差异和完整执行目标。
- 如果目的是防重复执行，消费 nonce 仅防止同一 nonce 再入；调用方可以重新预览获得新 nonce，失败重试也可能在外部已成功后重复产生副作用。若真有幂等需求，应另行围绕业务操作的结果语义设计，不能宣称 nonce 提供 exactly-once。

建议删除预览签名、密钥回退、nonce 消费表与清理任务；保留 preview、当前业务预检、差异确认和真实操作审计。若后续明确要求“执行的必须是刚才看到的版本”，再以显式预期版本作最小并发校验，且与已有“选择发布历史版本”的 `versionId` 字段区分。预览与发布接口可以保留，删除凭证不等于删除预检或默认确认差异。

### F2 · 修订稿新增机制本身又带来四项不闭合

1. `Hs256JwtService` 当前在配置密钥不足 32 字节时直接拒绝启动。预览服务新增随机回退，既不会让整个认证系统成功启动，又引入同一配置的第二套规则。随机回退不应成为修配置的旁路。
2. 使用固定配置密钥时，内存消费表在重启后清空、多实例间不共享，同一有效令牌可再次被另一实例接受；使用进程随机密钥时，跨实例/重启则无法验证。它只能提供进程内的有限去重，不能无条件称为“真正的一次性”。没有必要为此继续补 Redis/数据库。
3. 发布之前消费：外部发布失败也烧掉令牌；发布之后消费：并发可同时执行。消费表与 Dolphin 外部副作用没有原子提交边界。
4. 载荷以冒号拼接，但 `delegatedUserKey` 自身就包含冒号；还未绑定 operation、调度变更或 Dolphin 执行目标。继续修会增加序列化和快照规则，进一步说明应先论证必要性。

以上为代码与算法静态分析，没有执行重启、多实例或故障注入实验。

### F3 · P1：不可信委托头被扩展为数据库写身份

修订设计 §3.3.2 明确：SERVICE 携带 `delegatedUserKey` 时，物理 DDL 强制使用被委托 USER 的读写连接。该字段仍直接来自 `X-Agent-User-Id`；可信委托仍未实施。

此前只读查询是 USER 检查与 SERVICE 执行的交集，服务账号不能因提供用户名而超过自身数据库执行权限。修订稿的写路径则允许服务账号提供他人标识、改用他人的数据库写权限，原生数据库只识别实际登录的被委托账号，不能替平台验证委托可信性。

建议在可信委托落地前，SERVICE 触发的物理 DDL 始终使用 SERVICE 自身映射，当前用户头不能改变写入账号；若产品明确不允许带委托头写入，直接拒绝即可，但需在原设计选定一种规则。保持 23 个工具可用的决策不等于允许切换到未经证明的他人写身份。发布预览令牌即使绑定该头也无法补足这一信任来源。

### F4 · 结果预算的修订增加了数据与审计双份事实

修订稿新增默认截断单元格并追加 `...[truncated]`，会把合法 JSON 等数据值改成别的字符串；应该明确它是展示预览，优先保持保留行的值不变、超大行直接给出限制说明，不能让模型把改写结果当完整数据。

此外 core 先写查询历史，MCP 又可能按最终响应预算删尾行；两处 rowCount、hasMore 与审计预览可能不一致。应明确审计记录“数据库执行结果”还是“最终交付预览”，不要同时承诺同一份结果却由两层各自修改。最终体积校验应覆盖没有可裁剪 rows 的超长错误、DDL/元数据结果，不能假设删到空行必然满足总预算。

### F5 · 扁平 Schema 到领域对象的命名转换仍未定义

修订稿要求剥离 description 后直接 `ObjectMapper.convertValue`。但 MCP 建表字段包含 `db_name`、`doris_cluster_id`，`TableCreateRequest` 是 `dbName`、`dorisClusterId`，现有代码未为这些字段定义别名/统一 snake_case 策略。直接转换可能报未知字段或丢值。

建议把必要命名转换留在 MCP 适配边界，明确每个工具的强类型映射；不要为此修改全局门户 JSON 命名，也不要把“一份 Schema”误解为完全不需要协议适配。此类转换有真实职责，应保留；只删无职责的转发层。
