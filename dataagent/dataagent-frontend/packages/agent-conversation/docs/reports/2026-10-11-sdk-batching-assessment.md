# SDK 事件批处理与思考框性能评估

日期：2026-10-11。只做评估，没有修改产品源码、SDK dist、后端或宿主应用。

## 结论

建议保留事件批处理。普通短回答逐事件更新没有明显卡顿，但真实会话的 148 个持久化事件集中回放也能造成约 253ms 的主线程长任务；批处理后该回放约 47ms 完成，没有观察到 ≥50ms 的长任务。不能用单元测试中的 renderVersion 更新次数代替实际渲染性能证据。

去掉深度思考的边框、底色，或者进一步移除外层 section，没有值得优先处理的性能收益。思考默认折叠时不解析正文，展开预览有字符上限；装饰框不是本次瓶颈。可以按视觉设计决定是否去框，不需要以性能为理由。

另有一个长文本问题：MarkdownText 在模板中调用 markdown(segment.value)，组件收到新 text prop 时，即使 250ms 采样值未改变，也会重新调用 renderMarkdown。小文本由 HTML 缓存兜住，但原文和 HTML 总大小超过单条缓存预算（128000 字符）后，不再缓存，同一段采样文本可能反复 marked.parse。批处理减少了重复调用，但没有消除根因。LimitedText 的 HTML 使用 computed，不能将这一问题泛化为所有思考和工具文本。

## 环境与方法

- Node 20.19.0，通过仓库 nvm use 启动。Playwright 1.63.0，Chromium 153.0.8010.12，macOS 本机，无 CPU 节流，1100×900 viewport，1000×800 SDK 容器。
- 真实 Chromium 加载生产 Web Component 构建，使用自定义 transport 注入事件。测量真实 Vue 更新、DOM、布局和 Long Task，不使用 jsdom；未经过真实 SSE 网络、宿主 React 页面或模型执行。
- 两份构建只切换事件应用方式：当前 16ms 队列批处理，或恢复逐事件 processV2Record / renderVersion / triggerRef。其余当前工作区代码相同，包括 MessageItem 隔离和 250ms 文本采样。
- 组件更新钩子统计实际更新，marked.parse 调用计数与耗时帮助定位。另做完全移除这些探针的构建复核主要结论，下面的回放结果优先采用无探针数据。
- SDK 导入、历史快照加载和初始化不计入窗口；开始消费事件至 terminal 后两次 rAF 计为回放完成。主线程活动时间采用 CDP TaskDuration 差值，不等于整个流的墙钟时间。Long Task API 的 0 表示未观察到 ≥50ms 的任务，不表示没有工作。
- 回放每组 1 次预热 + 5 次新页面样本；4000 个事件压力回放 1 次预热 + 3 次样本；持续流每组 1 次缩短预热 + 2 次样本。交替批处理与逐事件的执行顺序。下面为中位数。

原始快照：447843 bytes，2 条消息，148 条 agent_event 记录，22 个工具、20 个思考块。SHA-256：a50ca9ce3d044e23988a84ce17989efdff3faf2b77c413b0f86e733eacb1acc6。原文件只读取，没有复制到仓库。

## 真实内容与人工压力输入的区别

20 条历史消息和 4000 个文本事件是独立参数：前者是人为重复原快照构造的历史列表；后者是向一条新回答注入的人工增量序列。4000 个事件并非从 20 条消息推导而来，也没有本次采集的真实运行事件频率作为依据。

原快照是任务完成后的持久化记录。topic_task_store 在成功结束后删除 content.delta，因此剩余 148 个事件不能用来推断原运行的完整事件数和时序。本次没有恢复这些已删除的增量。

为避免仅靠压力输入判断，首先原样回放真实快照的全部 148 条记录，只保留原用户消息并创建对应的实时助手消息。另将原答案的 1177 字文本人工拆成 295 个片段，每片最多 4 字，每 20ms 到达一个片段；这是基于真实内容的模拟流，时序仍是人工设定。

## 批处理对比

| 场景 | 逐事件更新 | 16ms 批处理 | 意义 |
| --- | ---: | ---: | --- |
| 原始 148 事件回放，至两帧完成 | 281.9ms | 47.1ms | 实际内容的集中回放已有可见阻塞 |
| 同上，最长主线程任务 | 253ms | 未观察到 ≥50ms 任务 | 批处理减少长任务 |
| 额外加入 20 条重复历史，148 事件回放 | 247.3ms | 31.9ms | 历史复用已预热部分 Markdown 缓存，不能与上一行直接比较历史增长的代价 |
| 1177 字答案模拟流，约 5.9 秒内主线程活动累计 | 175.4ms | 185.3ms | 两者均无 ≥50ms 长任务，低频流没有明显收益 |
| 人工 4000 文本事件集中回放，至两帧完成 | 2692.9ms | 73.7ms | 长文本、高密度增量的压力边界，不代表日常请求 |

原始 148 事件回放的无探针主线程活动累计时间为 285.8 → 48.0ms。逐事件回放的事件归并约 2ms、Markdown 解析约 7ms，其余开销主要来自随事件反复执行的 UI 更新；此处不是纯 Markdown 解析瓶颈。

人工长文本使用很多 Markdown 表格行，共 62411 字符，属于较重输入。带探针的 4000 事件回放中，逐事件更新执行约 4004 次 MessageItem 更新、4002 次 MarkdownText 更新、4005 次 Composer 更新；批处理各约 1 次。事件归并中位数约 12ms，Markdown 解析中位数约 3375ms。无探针复核依然有约 2.7 秒长任务，说明卡顿并非测量钩子制造。

在每秒 200 个人工增量、共 20 秒的长文本模拟流中，逐事件更新观察到最长约 2.36 秒的长任务，批处理未观察到 ≥50ms 的长任务；两者主线程活动累计约 9.34 秒与 4.25 秒。该输入同时放大了事件密度、文本长度和表格 DOM 数，不能作为正常用户流的延迟估计。

## 思考框对比

在同一轮带探针的 148 事件回放中，保留批处理，只改变思考框：

| 变体 | 主线程活动累计 | Layout 累计 | DOM 元素数 |
| --- | ---: | ---: | ---: |
| 保留思考框 | 47.6ms | 22.7ms | 445 |
| 去边框、底色、圆角 | 47.5ms | 22.8ms | 446 |
| 同时删除外层 section | 47.2ms | 22.8ms | 426 |

去框变体额外注入了一个测量用 style 节点，因此元素数多 1。删除 section 后少 20 个思考容器，但整体耗时只变化约 0.4ms。组件更新次数相同，正文、工具数量和最终答案检查均通过；思考按钮仍有可见高度。

另外测了折叠与展开的人工思考流（2000 个增量、10 秒、20 条重复历史）。去装饰框的主线程活动累计在折叠时约 668 → 657ms，展开时约 619 → 659ms，方向不一致，均未观察到 ≥50ms 长任务。展开只测默认的 4000 字预览，没有自动展开全部超长文本。

## 建议与边界

1. 保留有界事件批处理，尤其用于连接回放或同一网络块内的密集事件。单条消息的事件数量与文本长度、模型分片和工具调用有关，与历史消息数没有固定对应关系。
2. 把 MarkdownText 的 HTML 解析结果变为只随采样文本变化的 computed/子组件结果，避免依赖有大小上限的全局缓存来防止重复解析；单独覆盖超出缓存预算的长文本。
3. 修复取消路径：取消当前任务时在 stopStream 清空队列前刷新已接收事件；切换会话时继续丢弃旧队列。此评估没有修改该逻辑。
4. 思考框去留按视觉需求决定；性能优化优先处理重复解析和无关组件更新。

没有验证真实宿主完整布局、真实 SSE 分块频率、真实模型输出或低端设备。本报告证明当前 SDK 存在回放和长文本压力边界上的性能问题，不证明所有普通会话都会卡顿，也不证明宿主卡顿已全部解决。
